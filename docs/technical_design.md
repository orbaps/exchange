### 1.5 Order (Internal Engine State)

The `Order` object is the internal, mutable representation of an order inside the engine. It is never serialized directly — it is the working state from which `ExecutionReport` messages are constructed.

**Invariant enforced at every state transition:**
```
original_qty == cumulative_qty + leaves_qty + canceled_qty
```


### 1.6 Price Level

A doubly-linked list of `Order` objects at a single price, maintaining insertion order to preserve time priority. FIFO matching walks front-to-back; Pro-Rata iterates all nodes.

```mermaid
    PriceLevelImpl "1" o-- "0..*" Order : orders (time-ordered)
```

### 1.7 Order Book

One `OrderBook` instance per symbol. Manages the bid and ask sides as sorted maps of `PriceLevel` objects (descending for bids, ascending for asks). Owns the session state for this symbol and delegates matching to a strategy.

```mermaid
        -checkPriceBands(int64 price) bool
```

## 4. Sequence Diagrams

### 4.1 End-to-End Submission Lifecycle

From the moment a contestant uploads their code through to the final score appearing on the leaderboard.

```mermaid
sequenceDiagram
    actor C as Contestant
    participant SS as Submission Service
    participant OS as Object Store (S3)
    participant PG as Postgres
    participant BP as Build Pipeline
    participant TS as Trivy/Syft Scanner
    participant IR as Image Registry
    participant OR as Orchestrator

    C->>SS: POST /submissions {source_uri, manifest}
    SS->>SS: Validate manifest schema
    SS->>SS: Verify artifact checksum
    alt Manifest invalid
        SS-->>C: 400 Bad Request {errors}
    else Manifest valid
        SS->>OS: Store artifacts
        SS->>PG: INSERT submission record (status=PENDING)
        SS->>BP: Enqueue build job {submission_id}
        SS-->>C: 202 Accepted {submission_id}
    end

    BP->>OS: Download artifacts
    BP->>BP: Compile in isolated build VM
    alt Compilation fails
        BP->>PG: UPDATE submission (status=BUILD_FAILED)
        BP-->>C: Webhook: build failure
    else Compilation succeeds
        BP->>TS: Run SBOM scan (Syft)
        BP->>TS: Run vulnerability scan (Trivy)
        alt Scan finds critical CVEs
            BP->>PG: UPDATE submission (status=SCAN_FAILED)
            BP-->>C: Webhook: scan failure {findings}
        else Scan passes
            BP->>IR: Push contestant image (.so in container)
            BP->>PG: UPDATE submission (status=READY, image_ref)
            BP->>OR: Notify: submission ready {submission_id, image_ref}
            OR->>OR: Enqueue run
        end
```

## 5. State Machines

### 5.1 Order Lifecycle — Complete State Machine

Every order has exactly one state at any point in time. All transitions are triggered by specific engine operations and emit a corresponding `ExecutionReport`.

```mermaid
stateDiagram-v2
    [*] --> PendingNew : engine receives NewOrderRequest

    state "Validation" as val {
        PendingNew --> Rejected : INVALID_PRICE
        PendingNew --> Rejected : INVALID_QUANTITY
        PendingNew --> Rejected : INVALID_SYMBOL
        PendingNew --> Rejected : DUPLICATE_CLIENT_ORDER_ID
        PendingNew --> Rejected : SESSION_NOT_ACCEPTING
        PendingNew --> Rejected : FOK_WOULD_NOT_FILL
    }

    PendingNew --> New : Validation passes, order booked

    state "Active" as active {
        New --> PartiallyFilled : fill (leaves_qty > 0)
        New --> Filled : fill (leaves_qty == 0)
        New --> Canceled : CancelOrderRequest honored
        New --> Expired : TIF expiry (GFD at session close)
        New --> Replaced : ReplaceOrderRequest (price or qty change)
        New --> SmpCanceled : SMP triggered

        PartiallyFilled --> PartiallyFilled : fill (leaves_qty > 0)
        PartiallyFilled --> Filled : fill (leaves_qty == 0)
        PartiallyFilled --> Canceled : CancelOrderRequest honored
        PartiallyFilled --> Expired : TIF expiry
        PartiallyFilled --> Replaced : ReplaceOrderRequest
        PartiallyFilled --> SmpCanceled : SMP triggered
    }

    state "Replace Fork" as rfork {
        Replaced --> New : New order with new_order_id enters book
    }

    state "Terminal States" as terminal {
        Rejected --> [*]
        Filled --> [*]
        Canceled --> [*]
        Expired --> [*]
        SmpCanceled --> [*]
    }
```

**Transition Table:**

| From State | To State | Trigger | ExecType Emitted |
|:---|:---|:---|:---|
| `PendingNew` | `Rejected` | Validation failure | `REJECTED` |
| `PendingNew` | `New` | Accepted + booked | `NEW` |
| `New` | `PartiallyFilled` | Match, `leaves_qty > 0` | `PARTIALLY_FILLED` |
| `New` | `Filled` | Match, `leaves_qty == 0` | `FILLED` |
| `New` | `Canceled` | Cancel request | `CANCELED` |
| `New` | `Expired` | GFD at close / IOC remainder | `EXPIRED` |
| `New` | `Replaced` | Replace request | `REPLACED` |
| `New` | `SmpCanceled` | SMP triggered | `SMP_CANCELED` |
| `PartiallyFilled` | `PartiallyFilled` | Match, `leaves_qty > 0` | `PARTIALLY_FILLED` |
| `PartiallyFilled` | `Filled` | Match, `leaves_qty == 0` | `FILLED` |
| `PartiallyFilled` | `Canceled` | Cancel request | `CANCELED` |
| `PartiallyFilled` | `Expired` | TIF expiry | `EXPIRED` |
| `PartiallyFilled` | `Replaced` | Replace request | `REPLACED` |
| `PartiallyFilled` | `SmpCanceled` | SMP triggered | `SMP_CANCELED` |
| `Replaced` | `New` | New order ID enters book | `NEW` (on new ID) |

**Terminal state invariant:**
```
leaves_qty == 0
original_qty == cumulative_qty + canceled_qty
```

### 5.3 Exchange Session State Machine — Full Specification

```mermaid
stateDiagram-v2
    [*] --> Closed

    state "Session Startup" as startup {
        Closed --> PreOpen : SessionTransition(CLOSED → PRE_OPEN)
        note right of PreOpen
            Actions on entry:
            - Load GTC orders from last session snapshot
            - Orders accepted, booked (no matching)
            - Cancels and replaces allowed
        end note
    }

    state "Opening Sequence" as opening {
        PreOpen --> NoCancel : SessionTransition(PRE_OPEN → NO_CANCEL)
        note right of NoCancel
            Actions on entry:
            - Freeze: new orders accepted
            - Cancels BLOCKED
            - Replaces BLOCKED
        end note
        NoCancel --> Continuous : Uncrossing auction executes
        PreOpen --> Continuous : Direct uncrossing (no freeze period)
    }

    state "Active Trading" as trading {
        Continuous --> Continuous : Normal matching & execution
        note right of Continuous
            All operations allowed:
            - New orders, cancels, replaces
            - Continuous FIFO/ProRata matching
            - Stop-limit triggers checked after each trade
        end note
    }

    state "Disruption" as disruption {
        Continuous --> Halted : Circuit breaker (price band breach)
        note right of Halted
            Restricted mode:
            - New orders REJECTED
            - Cancels ALLOWED
            - Replaces BLOCKED
            - No matching
        end note
        Halted --> Continuous : Resume trading
        Halted --> Closed : Emergency close
    }

    state "Closing Sequence" as closing {
        Continuous --> PreClose : SessionTransition(CONTINUOUS → PRE_CLOSE)
        note right of PreClose
            Closing auction accumulation:
            - Orders accepted, booked (no matching)
            - Cancels and replaces allowed
        end note
        PreClose --> Maintenance : Closing uncrossing auction executes
    }

    state "End of Day" as eod {
        Maintenance --> Closed : Persist GTC, expire GFD, write snapshot
        note right of Maintenance
            Actions on entry:
            - Expire all GFD orders → ExecReport(EXPIRED)
            - Serialize GTC order state to snapshot file
            - Write final BookSnapshot
        end note
    }
```

**State Transition Matrix — Allowed Operations:**

| Current State | New Orders | Cancel | Replace | Matching | Stop Triggers |
|:---|:---:|:---:|:---:|:---:|:---:|
| `CLOSED` | ✗ | ✗ | ✗ | ✗ | ✗ |
| `PRE_OPEN` | ✓ | ✓ | ✓ | ✗ | ✗ |
| `NO_CANCEL` | ✓ | ✗ | ✗ | ✗ | ✗ |
| `CONTINUOUS` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `HALTED` | ✗ | ✓ | ✗ | ✗ | ✗ |
| `PRE_CLOSE` | ✓ | ✓ | ✓ | ✗ | ✗ |
| `MAINTENANCE` | ✗ | ✗ | ✗ | ✗ | ✗ |

### 7.2 Replay Procedure — Algorithmic Steps

```
PROCEDURE replay(journal_path, reference_output_path, snapshot_path=None):
    
    journal ← JournalReader.open(journal_path)
    reference ← load_reference_reports(reference_output_path)
    engine ← MatchingEngine.new()
    
    IF snapshot_path IS NOT None:
        snapshot ← load_snapshot(snapshot_path)
        engine.restore_from_snapshot(snapshot)
        journal.seek(snapshot.sequence_no + 1)
    
    output_reports ← []
    ref_index ← 0
    
    WHILE journal.hasNext():
        record ← journal.next()
        
        SWITCH record.payload:
            CASE NewOrderRequest, CancelOrderRequest, ReplaceOrderRequest:
                reports ← engine.onMessage(record)
                output_reports.extend(reports)
            CASE SessionTransition:
                reports ← engine.onMessage(record)
                output_reports.extend(reports)
            CASE BookSnapshot:
                SKIP  (snapshots are not replayed, they are verification checkpoints)
    
    // --- COMPARISON PHASE ---
    
    ASSERT len(output_reports) == len(reference)
    
    FOR i IN 0..len(output_reports):
        actual ← output_reports[i]
        expected ← reference[i]
        
        FOR field IN [sequence_no, execution_id, order_id, exec_type, 
                      last_price, last_qty, leaves_qty, cumulative_qty,
                      original_qty, reject_reason, match_order_id]:
            IF actual[field] != expected[field]:
                REPORT divergence at seq=actual.sequence_no, field=field
                RETURN FAIL
    
    RETURN PASS
```

| `order_id` | uint64 | Must be > 0 |

| `symbol` | string | Must match a defined instrument |
| `side` | Side | Must be BUY or SELL (not UNSPECIFIED) |

### 8.3 State Machine Validation — Legal Transition Matrix

The `StateMachineChecker` maintains a per-order-id state map and validates every incoming `ExecType` against this matrix:

| Current State | Allowed Next States |
|:---|:---|
| `(none)` | `PENDING_NEW` |
| `PENDING_NEW` | `NEW`, `REJECTED` |
| `NEW` | `PARTIALLY_FILLED`, `FILLED`, `CANCELED`, `EXPIRED`, `REPLACED`, `SMP_CANCELED` |
| `PARTIALLY_FILLED` | `PARTIALLY_FILLED`, `FILLED`, `CANCELED`, `EXPIRED`, `REPLACED`, `SMP_CANCELED` |
| `FILLED` | *(terminal — no further transitions)* |
| `CANCELED` | *(terminal)* |
| `EXPIRED` | *(terminal)* |
| `REPLACED` | `NEW` (on the new order ID) |
| `REJECTED` | *(terminal)* |
| `SMP_CANCELED` | *(terminal)* |

Any transition not in this matrix triggers a **FATAL** validation error.

### 8.4 Replay Diff Algorithm — Field Comparison Order

```
FUNCTION diff(expected: ExecutionReport, actual: ExecutionReport) -> List<FieldDiff>:
    diffs ← []
    
    // Compare in field declaration order (proto field numbers)
    COMPARE_FIELDS := [
        "sequence_no",        // 1
        "timestamp_ns",       // 2 — SKIP (engine timestamps may legitimately differ)
        "execution_id",       // 3
        "order_id",           // 4
        "client_order_id",    // 5
        "symbol",             // 6
        "side",               // 7
        "exec_type",          // 8
        "last_price",         // 9
        "last_qty",           // 10
        "leaves_qty",         // 11
        "cumulative_qty",     // 12
        "original_qty",       // 13
        "reject_reason",      // 14
        "match_order_id",     // 15
    ]
    
    FOR field IN COMPARE_FIELDS:
        IF field == "timestamp_ns":
            CONTINUE  // Logical timestamps are sequencer-assigned;
                       // engine processing time is telemetry, not correctness
        
        IF expected[field] != actual[field]:
            diffs.append(FieldDiff(
                field=field,
                expected=expected[field],
                actual=actual[field],
                order_id=expected.order_id,
                sequence_no=expected.sequence_no
            ))
    
    RETURN diffs
```

### 8.5 Validation Error Severity & Scoring Impact

| Severity | Effect on Run | Examples |
|:---|:---|:---|
| **FATAL** | Run result invalidated. Score = 0. | Missing fields, illegal state transition, broken quantity invariant |
| **CRITICAL** | Each divergence reduces correctness score. If correctness < 0.95, score = 0. | Wrong fill price, wrong fill quantity, priority violation |
| **WARNING** | Logged but does not affect score. | BookSnapshot level count mismatch (may be timing-related) |
